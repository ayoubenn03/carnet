## Piste à vérifier en priorité : est-ce l'entraînement ou la synchro ?

Deux jours sans la moindre écriture, ce n'est pas forcément deux jours sans
entraînement. Le carnet (`index.html`) écrit **toujours** dans le navigateur, et
n'envoie vers Supabase **que si la session est connectée** :

```js
async ecrire(o){
  localStorage.setItem(CLE, JSON.stringify(o));   // toujours
  if(sb && session){ ...upsert("carnet")... }     // seulement si connecté
}
```

Si la session a expiré, l'app continue de fonctionner normalement et l'athlète
n'a aucune raison de s'en douter : les séances s'empilent en local et
n'atteignent jamais la base. L'indicateur de synchro afficherait alors
`deconnecte` ou `erreur` plutôt que `cloud`.

**À faire, dans cet ordre :** ouvrir le carnet et regarder l'état de synchro en
haut. S'il n'indique pas `cloud`, se reconnecter — les séances stockées en local
seront alors remontées automatiquement (`store.lire()` réécrit le local vers
Supabase quand la base est vide). Si l'état est bien `cloud`, alors les séances
n'ont effectivement pas été saisies, et c'est le point 1 ci-dessous qui compte.

## Note technique

Les deux écarts signalés le 31/07 sont toujours présents, sans incidence sur le
résultat :

- `SUPABASE_URL` vaut `https://….supabase.co/rest/v1/` et contient déjà le
  suffixe, alors que la consigne le décrit comme l'hôte nu. Construire l'URL en
  `${SUPABASE_URL%/}/rest/v1/<table>` donnerait un chemin dupliqué
  (`/rest/v1/rest/v1/carnet`). Le suffixe est neutralisé avant l'appel.
- La clé fournie est au format `sb_secret_…` (clé secrète nouvelle génération),
  pas un JWT `service_role`. Elle fonctionne : `carnet` et `prescriptions` lues
  en HTTP 200.
